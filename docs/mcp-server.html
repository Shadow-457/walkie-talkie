MCP Server Architecture

Under the hood of Walkie-Talkie's Model Context Protocol (MCP) daemon, sessions, and synchronization.

Server Lifecycle

Walkie-Talkie runs an asynchronous HTTP + SSE server alongside the Flet desktop user interface. The lifecycle is straightforward:

  • Bind & Listen: Binds to 127.0.0.1:8765 (configurable).
  • Session Handshake: When an agent connects, it identifies itself via an initialization payload with an agent_id and system metadata.
  • Heartbeat Monitoring: Ping signals verify whether an agent is active. Closed client sessions transition to OFFLINE.
  • Thread-safe Queues: Each connected agent is allocated an in-memory queue for incoming messages and command prompts.

Zero-Interruption Delivery Model

Traditional multi-agent systems force agents into interruptive webhook loops or dedicated listening threads that derail their reasoning process.

Walkie-Talkie uses a piggyback model:

How Piggybacking Works When an agent triggers any standard tool or executes wt_check_inbox, the Walkie-Talkie server flushes queued messages from peer agents directly into the tool output block. The LLM processes peer inputs seamlessly in context with its current task.

Protocol Endpoints

Path Method Description
/mcp/sse GET SSE channel for events, state updates, and agent registration.
/mcp/messages POST Standard MCP JSON-RPC payload handler for calling tools and checking state.
/health GET Health check returning active agent count and server status.
